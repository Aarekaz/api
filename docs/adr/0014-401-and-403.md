# 0014: 401 for who you are, 403 for what you may do

Status: accepted, 26 Nov 2026 (branch `standards`)

## Context

`middleware/auth.ts` answered a missing Authorization header with 401, but a
header that wasn't `Bearer <token>` and a token it didn't know with **403**,
the same status as the website's token asking for an owner route. A client
couldn't tell "sign in again" from "this token will never be allowed", and no
401 carried the `WWW-Authenticate` challenge HTTP requires of it (RFC 9110
§15.5.2, RFC 6750 §3).

Who depends on the old status: the app (`../apple/Sources/OSCore/APIClient.swift`)
already treats a 401 as "the API token was rejected, update it in Settings" and
never branches on 403. The website sends a valid SITE_TOKEN and only checks
`res.ok`. The web OS checks `res.ok`.

## Decision

- **401** when there are no credentials or the API doesn't know them: no
  header (`WWW-Authenticate: Bearer`), another scheme, `Bearer` with nothing
  after it, or an unknown token, a signed-out device session included
  (`WWW-Authenticate: Bearer error="invalid_token"`).
- **403** when the token is known but may not do this: SITE_TOKEN outside the
  website's reads, or with `?include_unpublished`
  (`WWW-Authenticate: Bearer error="insufficient_scope"`).
- The body follows the route's dialect (ADR 0007): website paths keep
  `{ "error": "Missing authorization header" | "Invalid token" | … }`; every
  other path answers `{ "error": { "code": "unauthorized" | "forbidden", "message" } }`.
  The messages are unchanged.
- The presigned upload PUTs keep their own scheme (the `X-Upload-Token`
  header): missing is 401, a bad, expired or spent token is 403, because the
  token is a permission for one key, not an identity.

## Consequences

A client that retried or prompted on 403 for a wrong token now sees 401;
none of the three clients did. Tests: `__tests__/middleware/auth.test.ts`,
`site-token.test.ts`.
